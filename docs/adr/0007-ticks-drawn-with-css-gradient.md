# 0007: 目盛り線は CSS のグラデーションで描き、1区画の幅に応じて濃さを変える

- 状態: 採用
- 日付: 2026-10-24

## 状況

区画の境目に目盛り線を入れて、バーが何等分されているかを分かりやすくしたい。塗り領域は割合で配置していて、区画ごとの要素は作っていない（総数が大きくても要素数が増えない）。この性質を保ちたい。

区画が多すぎると、目盛りが密になって縞模様になり、かえって見づらくなる。目盛りを出すかどうかの基準は、分母だけでは決められない。バーの幅が変われば、同じ分母でも1区画の幅が変わるためである。

## 決定

- 目盛り線は、トラックの `::after` に `repeating-linear-gradient` で描く。DOM の要素は増やさない。
  - 総数は CSS 変数 `--inline-progress-total` で渡す。
  - 線は塗り領域の上に重ねる。
  - 右端（最後の区画の右）には線を引かない。
- 目盛り線を表示するかどうかは、1区画の幅（バーの幅 ÷ 総数）で決める。
  - 4px 以上: 表示する。
  - 4px 未満: 表示しない。
  - 境界の値は CSS 変数 `--inline-progress-tick-min-pitch`（既定 4px）で変えられる。
  - 計算の誤差で 4px ちょうどが消えないよう、0.01px 手前から表示に移る。
- バーの実際の幅は、トラックに `container-type: inline-size` を指定し、`100cqw` で取る。幅の指定方法（変数、直接の指定）に依存しない。
- 長さ ÷ 長さ（型付き算術）が使える環境でだけ、上の判定を有効にする（`@supports`）。
- 使えない環境では、分母が 32 を超えたら目盛りを消す。32 は、既定の幅（`8em`、16px で 128px）で1区画が 4px になる分母である。描画側は、分母が 32 を超えるときに `is-dense` クラスを付ける（`render.ts` の `DENSE_TOTAL`）。
- 線の太さと色は、CSS 変数（`--inline-progress-tick-width`、`--inline-progress-tick-color`）で変えられる。消したい場合は、CSS スニペットで `::after` を非表示にする。

1区画の幅の基準（4px）は、既定の幅で分母を変えながら描画し、等倍と2倍の画面で見え方を確認して決めた。8〜4px では区画を数えられ、3.5〜3px で縞模様に近づき、2.5px 以下では目盛りとして機能しなかった。4px を境に、表示と非表示の二択にした。

## 検討した代替案

- 境界付近で、幅に比例して目盛りを薄くしていく。表示と非表示の切り替わりは自然になるが、設定する値が2つ（完全に表示される幅と、消える幅）になり、見える・見えないの基準が分かりにくい。

- 分母だけで判断する（例: 32 以下のときだけ表示）。幅を変えると基準が合わなくなる。幅 `12em` では分母 48 でも見えるのに消え、幅 `4em` では分母 32 で縞になるのに表示される。
- JavaScript でバーの幅を測り、表示を切り替える。生成時点では要素が画面に載っておらず、幅が確定しない。`ResizeObserver` が要り、閲覧モードとライブプレビューの両方で扱いが複雑になる。
- 目盛り線ごとに要素を作る。総数に応じて要素が増える。
- 目盛りを出すかどうかを、記法のオプションや設定で選べるようにする。今回は求められていないので、見送った。必要になったときに足す。

## 結果

- 要素数は増えず、総数が大きいバーでも描画の負担は変わらない。
- 幅、文字サイズ、総数のどれが変わっても、目盛りの濃さが追従する。
- 型付き算術を使えるかどうかで、挙動が分かれる。
  - 手元の Chrome 155 と、Obsidian デスクトップ（同梱の Chromium 142、Electron 39.8.3）で使えることを確認した。モバイルの WebView では、使えるか確認していない。
  - 使えない環境では、分母だけで判断する動きになる。このとき、幅を小さくすると（例: 幅 64px で分母 32）、縞模様の目盛りが残る。
- 線の位置は、各区画の右端にある。境目をまたぐ中央ではなく、左側の区画の内側に引かれる。
- 見え方は、ヘッドレス Chrome と Obsidian デスクトップで確認した。既定の幅（128px）では分母 32 まで、幅 192px では分母 48 まで目盛りが表示される。
